MeterFlow: Usage Metering & Billing Engine

A multi-tenant backend that tracks usage, enforces quotas, and bills customers accurately for an AI-powered SaaS product, with correctness under concurrency as the central design problem.

role
FlyRank AI internship, accepted capstone
stack
FastAPI, PostgreSQL, Redis, Stripe
status
Capstone accepted, Stripe test mode

Overview

MeterFlow was the accepted capstone project for FlyRank AI's Backend AI Engineering internship track. The brief was a specific engineering problem: how do you meter and bill for AI usage correctly, not just track it, but guarantee the numbers a customer is billed for match what they actually used, even when the network retries requests or two requests arrive at once.

It's structured as a FastAPI backend with a React/TypeScript dashboard on top. The dashboard (typed API client, TanStack Query, protected routing) is supporting context. The interesting engineering is entirely in the backend: authentication, a two-stage quota gate, idempotent usage recording, weighted usage pricing, and Stripe-backed billing.

Problem

Usage-based billing sounds simple until you consider failure modes. A client's request to your API can time out and get retried by the client, a load balancer, or a flaky connection, and if each retry increments a usage counter, a customer gets billed for work they only requested once. At the same time, a metering system has to check remaining quota before letting an expensive AI call through, or you're paying for calls you can't bill for.

The problem MeterFlow solves: track usage per tenant, enforce per-plan quotas in real time, make sure duplicate requests never get recorded twice, and keep subscription state in sync with what Stripe has actually billed. Part of the work also meant auditing an existing codebase rather than starting from a blank slate, which turned up a real security bug (see Engineering Decisions).

Architecture

Every request passes through authentication and a quota check before it's allowed to reach the AI service, so a tenant that's out of quota is rejected before any cost is incurred, not billed after the fact.

Redis sits beside the request path as a fast idempotency and rate-limit check, not as a datastore of record. PostgreSQL, with a uniqueness constraint on usage records, is the correctness backstop.

Engineering Decisions

Two-stage quota gate. A fast pre-check blocks an obviously over-quota request before it reaches the AI provider at all. A second, authoritative check runs against real token counts once the response comes back. Splitting it this way enforces plan boundaries exactly without wasting provider calls on requests that were always going to fail.

Two-layer idempotency. Every usage-recording request carries an idempotency key. Redis is checked first, since it's fast and handles the overwhelming majority of duplicate retries. But Redis state can be lost or race under high concurrency, so a uniqueness constraint on the usage table in PostgreSQL is the actual guarantee: if two requests somehow get past the Redis check at the same instant, the database rejects the second insert.

Weighted, per-token-type pricing. Input, cached-input, output, and reasoning tokens aren't priced the same, so raw token counts don't map to cost. Usage is converted into a weighted charge against the plan price. Verified against a concrete case: 40% utilization on a $29 plan correctly bills $11.60.

Audit before building. The capstone started from an existing codebase rather than a blank one. Auditing it first, instead of building straight on top, surfaced a tenant-isolation bug (see Results) that would have been a real vulnerability in production.

Signature-verified Stripe webhooks. Subscription state (Free vs. Pro) is never trusted from the client. It's driven entirely by Stripe webhook events, with signature verification, so the database can't drift out of sync with what Stripe has actually billed.

Challenges

The main challenge was concurrency: proving that duplicate usage records genuinely can't happen, not just that they're unlikely to happen. That's what pushed the idempotency design to two layers instead of relying on Redis alone. Redis is fast but it isn't a durability guarantee.

A close second was the tenant-isolation bug found while auditing the existing codebase: cross-tenant requests were returning 200 OK when they should have been rejected. Finding a bug like that in someone else's code, understanding why it was wrong, and fixing it without breaking the tests that did pass took more care than writing the same logic from scratch would have.

Keeping billing state consistent without polling Stripe was a smaller, related problem. Webhook-driven sync solves it, but it meant handling out-of-order and duplicate webhook deliveries correctly too: the same idempotency thinking applied to a different part of the system.

Results

MeterFlow was reviewed and accepted as the capstone project for FlyRank AI's Backend AI Engineering internship track. It's a capstone project, not production software serving paying customers, so there's no live usage data to report, but the correctness claims below were verified with tests, not just asserted.

  • Found and fixed a tenant-isolation vulnerability: cross-tenant requests that previously returned 200 OK now correctly return 403 Forbidden, confirmed by automated tests.
  • Verified the idempotency guarantee by firing concurrent duplicate requests at the usage-recording endpoint and confirming exactly one record was ever persisted.
  • Verified the weighted-pricing calculation against a concrete case: 40% utilization on a $29 plan correctly bills $11.60.
  • Built and exercised a complete Stripe Checkout, webhook, and plan-sync flow in Stripe's test mode.

Lessons Learned

Correctness under concurrency has to be designed into the data layer, not bolted on afterward at the application level. A uniqueness constraint in Postgres did more real work here than any amount of in-memory checking could have. It's the kind of detail that's invisible until the one time it isn't, and then it's the only thing that matters.

Auditing an existing codebase before extending it is its own skill, separate from writing new code. The tenant-isolation bug wasn't something I would have introduced myself, but it was there to find, and finding it mattered more than any single feature I added on top.
